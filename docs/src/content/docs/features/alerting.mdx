Logchef evaluates alert queries on a schedule and sends notifications when thresholds are exceeded. Alerts fire via email (SMTP) and webhooks, so you don't need a separate alerting system.

## Quick Start

1. Navigate to your team/source → **Alerts** → **New Alert**
2. Choose a query mode supported by the source
3. Write a filter or native query
4. Set threshold: greater than 100
5. Set lookback: 5 minutes, frequency: 60 seconds
6. Add recipients and/or webhook URLs
7. Save

For ClickHouse, VictoriaLogs and Loki sources, an alert can be a LogchefQL condition, which the server compiles to the source's query language at every evaluation. Native mode remains available when you want to write SQL, LogsQL or LogQL directly.

## Query Modes

**Condition mode**: Write a LogchefQL filter condition and pick an aggregate function (`count`, `sum`, `avg`, `min`, `max`). For anything beyond `count`, also pick the field to aggregate over: schema-backed suggestions show all fields for VictoriaLogs sources and numeric columns for ClickHouse. On ClickHouse and VictoriaLogs, **Group by** names up to four fields, and each group fires on its own.

```
severity_text = "ERROR"
status_code >= 500 and service = "api"
body ~ "timeout"
```

The rule is stored as one LogchefQL aggregation, with `query_language` set to `logchefql`:

```text
status_code >= 500 | count() as value by service
```

The server compiles it at every evaluation, for the lookback that ends at the evaluation time, so a test, a backtest and the scheduled run read the same query. Through the API, the query takes one aggregate and no `time` key, and `group_by` may be left empty: the `by` keys fill it. A window where the aggregate had no numeric input, such as `sum` over no matching row, counts as no data and follows the rule's no-data policy. A condition saved before the server compiled conditions keeps the native query the form generated and runs it unchanged; saving it from the form stores it as LogchefQL.

**Native mode**: Write the source's native alert query. The query must return a single numeric value.

```sql
SELECT avg(JSONExtractFloat(log_attributes, 'response_time_ms')) as value
FROM logs
WHERE service = 'api-gateway'
  AND timestamp >= now() - toIntervalSecond(600)
```

For VictoriaLogs sources, native mode uses LogsQL and evaluates through `stats_query`. Logchef applies the configured lookback window automatically, so the query can stay focused on the filter and stats logic.

```text
level:="error" | stats count() as value
```

For Grafana Loki sources, native mode takes a LogQL metric query, evaluated as
an instant query at the run's due time. The range in the query, such as
`[5m]`, decides what is counted, and Logchef does not rewrite it. The form
still asks for a lookback, because backtests use it, and warns without
blocking a save when the query has no range equal to the lookback. Condition
mode on Loki compiles the filter into `count_over_time` for `count`, and into
`unwrap` with `sum_over_time`, `min_over_time`, `max_over_time` or
`avg_over_time` for the other aggregates, over a range equal to the lookback.
A Loki condition cannot group; write a native LogQL query with `sum by (...)`
for that. A log query is refused with "A Loki alert needs a metric query".

```text
sum(count_over_time({service_name="payments-api", level="error"} [5m]))
```

## Alert Configuration

| Field | Description |
|-------|-------------|
| Name | Human-readable identifier |
| Severity | `info`, `warning`, or `critical` |
| Query | LogchefQL condition, ClickHouse SQL, VictoriaLogs LogsQL or Loki LogQL depending on source |
| Threshold | Value + operator (`>`, `>=`, `<`, `<=`, `==`, `!=`) |
| Frequency | Evaluation interval in seconds |
| Lookback | Time range for the query |
| Recipients | Team members to email |
| Webhook URLs | HTTP endpoints to POST payloads to |

## Notifications

### Email (SMTP)

Configure SMTP in **Administration → System Settings → Alerts**:

| Setting | Example |
|---------|---------|
| SMTP Host | `smtp.example.com` |
| SMTP Port | `587` |
| SMTP Security | `starttls` |
| SMTP From | `alerts@example.com` |

### Webhooks

Add webhook URLs per alert. Logchef POSTs a JSON payload containing:

- Alert name, severity, status (`triggered` / `resolved`)
- The query result value and threshold
- Labels (team, source, custom key-value pairs)
- Annotations (description, runbook URL, query text)

Works with Slack incoming webhooks, PagerDuty, or any HTTP endpoint.

### Labels and Annotations

Add custom labels for routing and annotations for context:

```json
{
  "labels": { "env": "production", "service": "payment-api" },
  "annotations": { "runbook": "https://wiki.example.com/high-error-rate" }
}
```

## Reliability

- Failed deliveries retry with exponential backoff (500ms → 1s → 2s)
- Delivery outcomes recorded in alert history
- Resolution notifications sent when conditions clear

## Dashboard

The alerts list shows live status for each rule:

- Toggle alerts on/off directly from the list
- Red pulsing dot = firing, green dot = resolved
- Duplicate existing alerts for similar conditions
- View full evaluation history per alert

## SMTP Configuration (First Boot)

Seed initial settings via `config.toml`. After first boot, use the Admin UI:

```toml
[alerts]
enabled = true
smtp_host = "smtp.example.com"
smtp_port = 587
smtp_from = "alerts@example.com"
smtp_security = "starttls"
```

`enabled` is the **server-wide** alerting switch. With `alerts.enabled = false`
(or `LOGCHEF_ALERTS__ENABLED=false`) Logchef hides all alerting UI and every
alert endpoint returns `503`. That's useful for exploration-only deployments.
Each rule is evaluated at its own frequency (at least 10 seconds) on whichever
replica claims the tick; see [Postgres backend](/operations/database-backends/)
for running several replicas.

## Troubleshooting

**Alerts not firing:** Check the alert is enabled, test the query manually, verify the threshold makes sense for your data volume, and confirm the selected query language matches the source type.

**Alerts not delivered:** Verify SMTP settings, check that recipients or webhook URLs are configured on the alert, review delivery status in alert history.

**False positives:** Increase the threshold, extend the lookback window, or use `avg()` instead of `count()` for smoother signals.

For backend-specific guidance, see [Using VictoriaLogs with Logchef](/tutorials/victorialogs) and [Using Grafana Loki with Logchef](/tutorials/loki#alerts).
